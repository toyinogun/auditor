# 0003. Sample data generator: rationale

## Context

The brief says the demo runs only on fictional data "generated by a script as real PDFs + 2 CSVs", and the scope puts the generator before the checks and before any LLM or UI work. Its output feeds three later features at once: offline mode loads the documents without an API key (feature 6), a real extraction run must reproduce the same findings from the PDFs (feature 7), and ingest dedupes documents by sha256 and, on the public demo, must accept only the sample files (feature 8). The headline number, $9,766.85 over 8 findings, depends on every figure being printed exactly.

Spec 0002 already put every document into `lib/schemas/fixtures/brief-sample.ts` as extraction shapes, with dates, clauses and payment references filled in where the brief is silent. What does not exist is anything a person or a model can actually read: the PDFs and CSVs themselves. The brief also asks that one invoice be a scan with no text layer, to prove the model can read page images.

The forces are: exact figures with no second copy to drift; files that look like real business documents in a portfolio demo; one image only invoice; output stable enough that sha256 dedupe and a git diff mean something; a 2 to 3 evening time box; and the stack in spec 0001 (Node 22, TypeScript, pnpm, Vitest, one Docker image). Without a decision, each consumer would guess at filenames, hashes and which invoice is scanned, and the offline path and the LLM path could quietly disagree.

## Options considered

### Option 1: pdfkit text PDFs plus a canvas drawn scan, from one page model, committed

Render each document from the fixture into a small list of drawing operations, paint it with pdfkit for text PDFs, and paint the NL88310 page onto @napi-rs/canvas for the scan, which pdfkit then wraps as a one image PDF. Commit the output to `public/sample/` with a manifest, and guard the bytes with a test.

**Pros**:
- pdfkit is actively maintained, embeds TTF fonts with a stable subset name, and derives its file ID from the info dates, so fixing those dates gives stable bytes.
- One layout serves both painters, so the scan matches NL-88310 exactly.
- Canvas with a committed font never touches system fonts, so the scan does not change with the machine's installed fonts.
- Committed output keeps the Docker image free of PDF tooling.

**Cons**:
- You own a small drawing abstraction and its paragraph wrapping.
- Two new rendering dependencies, one of them native (prebuilt).
- Skia rendering may differ slightly across platforms, which can break byte identity of the scan on another OS.

### Option 2: HTML templates printed to PDF by a headless browser

Write each document as an HTML page styled with Tailwind, print it to PDF with Playwright's Chromium, and screenshot the NL88310 page for the scan.

**Pros**:
- Layout with real CSS; easy to make beautiful.
- Reuses the web styling you already know.

**Cons**:
- Pulls a full browser into dev dependencies.
- Chromium stamps creation dates and IDs into each PDF; getting byte identical output means post processing the files.
- Screenshots depend on browser version and font rendering, which moves more often than a pinned library.

### Option 3: pdf-lib for text PDFs, pdf.js rasterization for the scan

Draw each PDF with pdf-lib, then rasterize NL-88310 through `unpdf` with a canvas backend and embed that image as NL88310.

**Pros**:
- One drawing path; the scan is literally a picture of the text PDF.
- pdf-lib is pure JavaScript.

**Cons**:
- pdf-lib has had no release since 2021 and is low level (every string placed by hand).
- Embedding a custom font in pdf-lib adds a random suffix to the font name unless overridden, a quiet source of changing bytes.
- Rasterizing through pdf.js depends on its standard font data setup, which varies by configuration.

### Option 4: Make the PDFs once by hand and commit them

Lay out the 12 documents once in a design tool, export them, scan or flatten one, and commit the files. No generator code.

**Pros**:
- Fastest to a first file, full visual control.
- Nothing to maintain.

**Cons**:
- The figures live in a second place that nobody can diff against the fixture.
- Does not meet the brief's "generated by a script".
- Any correction means redoing the file by hand.

## Rationale

Option 1 wins because it is the only one that keeps a single source of figures (the fixture) while still producing stable bytes without post processing. The sha256 dedupe in spec 0002 and the demo upload allowlist in feature 8 both depend on the bytes not changing between runs, and pdfkit gives that with nothing more than fixed info dates. Option 2 would look nicer for the same effort, but a browser in dev dependencies and date stamped PDFs is a lot of moving parts for 15 files. Option 3 has the tidiest scan story, but a stale library plus a font naming trap works against the byte stability that matters most here. Option 4 fails the brief outright.

The scan is NL88310, the reminder copy. A reminder that came back as a paper scan is the realistic story, and it carries the largest finding ($8,141.00, paid twice), so the demo proves the scan path on the headline number. Its duplicate detection uses the normalized invoice number, so a model reading `NL88310` or `NL 88310` still matches. The scan look is kept light so legibility stays high.

Output goes to `public/sample/` and is committed: visitors can open the PDFs from the demo, the standalone Docker image already copies `public/`, and a PR shows exactly which files changed. The manifest saves features 6 and 8 from each hashing files their own way.

**Smaller calls settled while writing** (pick, why, runner up):
- **One page model, two painters** (pdfkit and canvas), so the scan and NL-88310 cannot drift apart. Runner up: separate canvas code for the one scanned invoice, which is less code today but a second layout to keep in step.
- **Printed dates in long US form** (`April 3, 2026`): unambiguous, realistic, and a fair test of the model's date normalization. Runner up: ISO dates, which make extraction too easy to prove anything.
- **Printed money as `formatCents(parseMoney(x))`** (`$15,600.50`), reusing the spec 0002 helpers so no float touches money. Runner up: bare fixture strings, which look unfinished on a business document.
- **US Letter pages**, since the buyer is American and the currency is USD. Runner up: A4.
- **Inter** (OFL licence) regular and bold as the one bundled font. Runner up: IBM Plex Sans; both are fine, Inter has the better small size numerals.
- **Scan at 200 DPI grayscale PNG**: sharp enough for the model, lossless so the bytes are stable. Runner up: JPEG, which looks more like a real scan but adds encoder variation.
- **mulberry32 with a fixed seed** for the scan effects: a tiny, well known seeded generator. Runner up: a hash of the invoice number as the seed, no real gain.
- **PDF info dates set to the document's own date at 12:00 UTC**, which reads naturally in a PDF viewer. Runner up: one fixed date for every file.
- **CSV as UTF 8, LF line endings, trailing newline, RFC 4180 quoting only when a cell needs it.** Runner up: CRLF, which Excel does not need.
- **Contact details on `example.com` and 555 01xx numbers**, reserved for fiction, so no real business can be reached or named.
